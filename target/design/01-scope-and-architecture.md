## 3. 技术选择与必要依赖

- 前端：现有 Vue3 + TypeScript + Ant Design Vue + Pinia + vben 组件，不增加 UI、图表或工具库。
- 第一阶段后端：复用 `apps/backend-mock` 的 Nitro/H3 与现有依赖，提供与正式 API 一致的请求/响应、权限和业务状态模拟；前端统一走 requestClient，不在页面写死模拟数据。
- 第二阶段后端：新增 `apps/api` 独立 Go module；使用标准库 `net/http`，按 handler / service / repository / request-response struct 组织模块；构造函数显式组装依赖。
- 数据库：第一阶段在根目录 `database/migrations` 编写 PostgreSQL 建表迁移、在 `database/seeds` 编写初始数据，独立于后端语言；第二阶段 Go 使用同一份 SQL 和 `github.com/jackc/pgx/v5` 及其 pgxpool 访问数据库，不引入 ORM。
- 必要直接 Go 依赖为 `pgx/v5`（数据库）和 `golang.org/x/crypto` 中 scrypt（密码派生）。HTTP、JSON、日志、配置、随机令牌使用标准库；版本在实施时按工具链兼容性确定。此轮不安装依赖或修改锁文件。
- 前端继续使用原 Node/pnpm 工具链；后端使用 Go 工具链。暂不增加 Gin、Redis、消息队列服务、微服务框架、通用工作流引擎或新的开发工具。
- 认证采用 `crypto/rand` 生成随机会话令牌，数据库只保存令牌摘要；密码使用带独立盐和参数的 scrypt。前端仍按 Bearer token 调用。
- 单实例开发可使用本地上传持久目录；多实例部署前必须使用各实例共同可访问的文件存储。文件读取检查权限，合同、人脸等附件不直接暴露静态 URL；实际存储服务选择到部署时确定。
- 优惠券额度分配、发券和消息等分别使用业务批次表和 PostgreSQL 持久任务执行，显示逐项结果；事务及唯一键保证重试不重复加额度或发券。

上述依赖用于数据库连接及账号安全，属于后端必要依赖；如后续需要与业务无关的第三方库或工具，再说明必要性并征求同意。三万日活不构成必须使用 Go 的结论，容量假设、连接池及扩容边界见后端设计文档。

## 4. 第一版边界与待定业务语义

| 项目 | 提案 / 需要明确的内容 |
| --- | --- |
| 一键维护 | 已明确为授权范围内的批量业务操作；第一版覆盖批量分配门店优惠券张数、批量发券、批量消息。每项操作复用对应业务权限/校验，不提供任意表字段批量修改入口 |
| 门店优惠券额度 | 已明确按券模板可发张数计算；总部向选定门店或全部适用且启用门店追加额度，门店发券消耗额度；总部代门店发券同样计入该店额度 |
| 工资模板 | 支持底薪、会员卡销售提成、私教销售提成、消课提成、固定加扣项；规则版本与计算明细留存。实际比例由总部配置，未配置不得猜测工资 |
| 平均业绩 | 沿用已审阅口径：分别返回员工人均业绩（含零业绩有效员工）和订单均额；实收减退款，按统计期支付/退款发生日计算 |
| 通卡会员前缀 | 提案为发卡时保存“发卡门店名称 + 总部模板前缀 + 卡号”的展示快照；跨店使用不改变来源门店 |
| 连续包月、自助核销、在线售卡 | 第一版配置、查看记录；不新增会员下单、扣款授权、兑换入口 |
| 积分兑换 | 第一版总部配置规则、兑换商品、查看流水/兑换记录；会员兑换接口留待后续 |
| 合同 | 第一版上传模板、管理/查看记录、发起提醒；不提供会员签名接口。签署内容来自后续签约渠道，禁止在后台直接伪造 signed 状态 |
| 小程序/App 码 | 保存管理端生成的场景与渠道。真实小程序码需 AppID/凭证，App 码需已确定的落地链接；签课码消费接口不在第一版 |
| 私信、批量推送、未签约提醒 | 管理端创建并查询投递任务；需要消息渠道及凭证才能实际送达会员 |
| 远程开门/开柜 | 需要设备品牌/协议/网关；只有设备确认成功才显示成功，排队、超时、失败分别显示 |
| 收款账户绑定/分账 | 后台配置比例、周期、查看记录；真实账户绑定需支付渠道接入，保存配置不等于渠道绑定成功 |
| 其他端专属业务 | 训练计划上传、会员分配操作、私教链接购买/改价申请、自动门禁风控、入场推送、下载奖励等只预留数据；不因建表添加页面或接口 |

第一阶段使用明确标识的 Mock 场景模拟渠道成功/失败/等待状态，供页面交互开发，不代表已发生真实付款、投递、签约或设备动作。第二阶段真实接入时需用户提供支付/分账渠道、设备协议、消息渠道、签约渠道及小程序/App 跳转配置；无配置返回明确“未配置”，不能用假成功代替接入。厂商回调/设备回传属于真实集成时需要另行明确的服务间接口，不在本次管理端 REST 清单中暗中增加。

## 5. 两阶段实施顺序与提交

### 第一阶段：前端 + Mock 后端 + 数据库

- 使用 `apps/web-antd` 完成总部/门店管理页面；使用 `apps/backend-mock` 完成对应管理端接口模拟，不提前实现 Go 服务。
- Mock 支持新增/编辑后再次查询可见、分页筛选、总部/门店权限、批次进度与常见错误，不只返回固定成功。模拟数据的初始化/重启行为随模块说明。
- 数据库交付可执行迁移、外键/索引/检查约束，以及权限等初始数据；开发示例数据与正式初始化分开，覆盖全部需求实体及未来端预留结构。
- Mock 场景中的门店/会员/模板 ID 和数据库示例数据保持一致。第一阶段分别完成页面与 Mock 联调、SQL 建表和关联验证；Mock 操作暂不要求写入真实 PostgreSQL，真实读写联调放第二阶段。
- 第一阶段按下面的业务顺序逐模块实现页面、Mock 与数据库脚本，每个模块完成后独立提交。

1. 数据库迁移目录与基础结构、Mock 管理员登录、角色/门店数据范围和管理端导航。
2. 门店、文件上传、员工与权限。
3. 会员、本店关联、会员卡种/通卡、会员详情与总部汇总。
4. 签到查询、课程安排、预约、上课记录、体测。
5. 合同模板/记录/提醒、审批模板/审批记录。
6. 设备/远程命令、器械教学、黑名单。
7. 在线售卡/包月/核销设置及记录、会员卡报表。
8. 积分、优惠券及门店额度、礼品码、批量管理与消息。
9. 活动、小程序内容、加盟信息、评价/匿名反馈。
10. 收款账户与分账设置、薪资规则及工资表。

第一阶段结束前，所有需求实体（包括其他端预留表）必须有实际 SQL 结构，不能只停留在设计文档；所有第一版网页模块有对应的 Mock 交互。

### 第二阶段：Go 后端

第一阶段完成后，再实现 Go 入口、配置、认证/权限、数据库访问及迁移命令，按相同业务模块顺序实现正式 API 和 worker。沿用第一阶段的 SQL 与 HTTP 契约，前端通过代理/环境配置切换到 Go，不重写页面业务流程。Mock 不能保证的事务、持久化、并发额度、幂等和实际渠道接入在这一阶段落实并验证。

第二阶段每个后端模块完成后独立提交；最终由现有网页操作真实数据库，核实数据持久化、门店权限与业务结果，并按实际接口完成必要容量验证。Mock 联调不能替代这一步，也不能当作三万日活承载证据。

两阶段均只进行必要的接口调用与联调，不增加用户排除的额外工程流程，不做 UI 美化，不新增其他端前端或接口。

## 6. 当前决策与后续实施

原范围、数据模型和 API 方案已获确认，无需重复请求整体批准。按用户最新指示先完成前端/Mock/数据库，再做 Go；工资/业绩/通卡前缀沿用已审阅方案，实际数值由总部配置。第一阶段不因 Go 工具链或外部渠道资料尚未到位而阻塞页面与 Mock 开发。
