## 已定决策

### D-05 后端采用 yudao（已定）

- 背景：原规划为自研 Go 后端；现确定使用芋道 yudao 全家桶。
- 结论：`yudao-server`（Spring Boot + MyBatis Plus + Redis）+ 自研 `yudao-module-gym`。
- 影响：`target/design/04-backend-design.md` 失效；`database/` 旧 PostgreSQL 设计仅作字段参考。

### D-06 移动端采用 uni-app 一套代码（已定）

- 结论：一套 uni-app 代码发布微信小程序 + iOS/Android APP（+ 可选 H5），同端按角色显示会员/员工/管理者/总部功能。
- 影响：`02-scope.md` 中“小程序/APP”同源；推送、打包、上架为独立工作项（R43）。

### D-07 门店以部门（dept）建模（已定）

- 结论：总部/门店用 `system_dept` 树；门店隔离用 yudao 数据权限。
- 影响：需为自研 `gym` Mapper 显式接入数据权限；多店任职另建关联表。

### D-08 范围以 R01–R43 为准（已定）

- 结论：附件一 R01–R43 为唯一范围基准；排除项不投入；新增走书面补充协议。

## 已确认决策（2026-09-29 甲方拍板）

> D-01 ~ D-04、D-09 已拍板，结论见各条“结论”行；未定的只剩设备/第三方资料的“待甲方提供”。

### D-01 管理端基座（已定：选项 A，yudao-ui-admin-vben）

| 选项 | 优点 | 缺点 |
| --- | --- | --- |
| A. `yudao-ui-admin-vben`（vben/AntD）**（推荐）** | 与现有工程同框架，现有 gym 页面可迁移；免费获得 yudao 系统/BPM/支付/会员/IoT 页面；`feat/yudao-api-adapter` 适配思路可复用 | 需对齐 yudao 管理端版本与目录；部分模块页面可能滞后于 vue3 版 |
| B. 保留 `apps/web-antd` + 适配层 | 现有 60+ 页面零迁移 | 需自研全部 yudao 模块页面与接口；适配层长期维护成本高 |
| C. `yudao-ui-admin-vue3`（Element Plus） | yudao 模块页面最全、社区主流、代码生成默认 | 健身房页面需从 AntD 迁移到 Element Plus，前端重写量大 |

- **结论：采用 A**。本仓库与 yudao-ui-admin-vben 同为 vben 5.7 + Ant Design Vue monorepo，迁移以“合并”为主；方案见 `07-frontend-port.md`。
- 已提交的 `feat/yudao-api-adapter` 适配层可复用（`VITE_API_BACKEND=yudao`）。

### D-02 数据库（已定：选项 A，MySQL 8）

| 选项 | 优点 | 缺点 |
| --- | --- | --- |
| A. MySQL 8 | yudao 官方 SQL / 代码生成 / Flowable / 文档默认；生态最顺 **（推荐）** | 放弃现有 PostgreSQL 迁移；需迁移工具与运维调整 |
| B. PostgreSQL | 与现有 `database/` 一致 | yudao 的 SQL/代码生成/部分模块以 MySQL 为主，需自维护兼容，风险与工期成本高 |

- **结论：采用 A（MySQL 8）**。当前机器非开发机，MySQL/Redis/yudao-server 的落地与联调延后到开发机；现有 PostgreSQL 迁移仅作业务字段参考，不作为交付库。

### D-03 旧原型中超范围功能处置（已定：选项 A，隐藏冻结）

合同 R01–R43 未纳入：优惠券发放、积分、礼品码、批量消息、操课管理、临期筛选、展示素材、潜客跟进、多人报警、带人冻卡、夜间滞留等。

| 选项 | 说明 |
| --- | --- |
| A. 隐藏/冻结，代码保留不投入 **（推荐）** | 保留历史实现以备未来补充协议；不纳入交付与维护 |
| B. 直接删除 | 与合同范围最一致，但丢弃历史资产 |
| C. 继续完善 | **不建议**：超出合同范围，挤占工期 |

- **结论：采用 A**：在管理端隐藏入口、在文档标注“合同外/不维护”。

### D-04 yudao 版本分支（已定：选项 A，JDK17/Spring Boot 3.5）

| 选项 | 说明 |
| --- | --- |
| A. `master-jdk17`（JDK17/21 + Spring Boot 3.5）**（推荐）** | 现代长期支持栈，适合 2026 年新项目 |
| B. `master`（JDK8 + Spring Boot 2.7） | 兼容性最广、模块最全，但技术栈较旧 |
| C. `master-jdk25`（JDK25 + Spring Boot 4） | 最新，生态与第三方兼容风险较高 |

- **结论：采用 A（`master-jdk17`）**；选型时**逐模块核对** IoT/BPM/pay 等是否在该分支可用，必要时回退 B（JDK8/SB2.7）。

### D-09 整合客户端身份（已定：选项 A，双 token）

| 选项 | 说明 |
| --- | --- |
| A. 双 token（member + system）**（推荐）** | 复用 yudao 原生认证；APP 同时持有 C 端与 B 端 token，按角色显示工作台 |
| B. 自定义统一登录签发单 token | 体验与实现简洁，但偏离 yudao 原生认证，改造大 |

- **结论：采用 A（双 token）**；若登录/续期体验明显受损，再评估 B。

### D-10 通知推送通道（推荐 uni-push；通道与证书待甲方提供）

- 推荐 **uni-push**（与 uni-app 同源，改造最小）；备选个推/极光。小程序订阅消息使用微信能力。
- 通道未定期间先实现消息中心与通知抽象，推送后补并标注“未接入”。
