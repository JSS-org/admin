# 02 · 合同范围矩阵（R01–R43）

> 依据：`target/健身房合同_三附件签署稿/附件一_项目需求说明书.docx`（范围基准）与附件二（验收基准）。
> **R01–R43 全部纳入合同总价**；本表用于排期、确认与验收追溯。状态列区分“合同交付状态”与“旧原型资产”。

## 1. 图例

- **端**：`小程序`（整合会员/员工/管理者）、`APP`（整合三端 + 系统推送）、`管理端`（总部/门店网页，同后台分角色）、`后端`、`IoT`。
- **承载**：`yudao-*` = 直接复用芋道模块；`gym` = 自研健身房业务模块；`bpm` = yudao 工作流（Flowable）。
- **现状**：`未开始` = 按合同尚未开工；`原型页` = 旧范围 vben 原型存在可参考页面/流程（**不代表合同验收通过**）；`旧设计` = 仅旧文档有设计。

## 3. 明确排除项（不构成交付与验收义务）

合同附件一“实施安排”明确排除：

- IoT 风控类：多人入场报警、会员带人超次冻结卡、夜间异常滞留提醒、欠费禁止入场。
- 潜客类：潜客分配及跟进（仅保留登录形成的潜客记录）。
- 运营工具：一键维护、批量消息、优惠券发放、礼品码、操课管理、临期筛选。
- 展示素材：展示及素材功能（门店展示内容由既有配置项承载，见 R33）。
- 会员手机号/人脸资料变更由有权管理员人工办理，不提供会员自助变更。

> 规则：新增上述能力或对已实现规则做**结构性调整**，一律走书面补充协议（合同第 2.2–2.4 条），不在本规划内投入。

## 4. 验收与证据映射

- 每个 R 的验收要点见附件二，实现时按 R 编号建立**测试用例 → 证据**记录。
- 里程碑检查（附件二“阶段及交付检查”）：A = 后台 + 必要后端；B = 全部客户端 + 联调 + 角色导航 + 通知权限；C = 全部交付物移交确认。
- 第三方未接入的能力（支付/设备/推送/电子签/团券）必须标注“未接入”并走附件二“暂缓/补验”，**禁止假成功**（合同第 5.6、6 条）。
