# 04 · 里程碑与敏捷实施计划

> 合同工期：项目启动日起 **6 个自然月**（前 3 个月里程碑 A、其后 3 个月里程碑 B），全部开发款付清后 **3 个自然月支持期**（合同第 4.2/9 条）。
> 本文件给出可执行的分阶段迭代；**每个迭代 = 一个可验证增量 = 若干小提交**，对应 R 编号与附件二证据。

## 1. 阶段总览

| 阶段 | 目标 | 对应 | 建议周期 |
| --- | --- | --- | --- |
| P0 基座 | yudao 落地、模块选型、账号/门店/权限、`gym` 模块骨架、管理端基座、CI | 前置 | 2–3 周 |
| P1 后台与必要后端 | 管理端 + 后端业务，达到里程碑 A | R29–R38、R42 及 A 所需后端 | P0 起 3 个月内 |
| P2 整合客户端与联调 | 小程序 + APP 三角色、通知权限、第三方联调，达到里程碑 B | R01–R28、R39–R43 | P1 后 3 个月内 |
| P3 交付确认 | 源码/构建包/数据库/脚本/文档/权限移交，里程碑 C | R42、交付物 | P2 完成后 |
| P4 支持期 | 提审上架、生产部署、试运行、缺陷修复 | 合同第 9 条 | 付清后 3 个月 |

> P0/P1/P2 的分界是**合同里程碑**，不是技术模块。里程碑只认“可操作的后端 + 客户端”，不接受仅原型/模拟（附件二）。

## 3. 敏捷机制（小步提交）

- **以 R 编号管理 backlog**：每个 R 拆成若干 1–3 天增量；增量完成即提交 + 更新 `01-status.md`。
- **提交粒度**：一个业务增量一次提交；提交信息中文 conventional commits 并带 R 编号，例如 `feat(gym): 门店资料 CRUD (R29)`。
- **分支**：`feat/<模块>-<R编号>`、`fix/<问题>`、`docs/<主题>`；主干保持可构建。合并前跑 `pnpm vsh lint --format`、`pnpm --filter @vben/web-antd typecheck`、`pnpm vitest run apps/web-antd --dom`（后端工程按对应构建/单测）。
- **DoD（完成定义）**：功能可用 + 权限/门店隔离校验 + 单测/证据 + 文档/状态更新；第三方未接入必须标注“未接入”，禁止假成功。
- **周报**：合同第 3.5 条要求每周书面进度/风险/下周计划；模板见 `06-workflow.md`。

## 4. 关键路径与风险

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| yudao 学习曲线 + 版本/模块膨胀 | P0/P1 超期，威胁里程碑 A | P0 先最小可用集；只引入与 R 相关模块；D-04 尽快定版 |
| 管理端基座未定（D-01） | 前端返工 | 立即拍板；未定前只做与 UI 无关的后端/接口 |
| 数据库未定（D-02） | 建表与 SQL 返工 | 尽快定；未定前避免大规模写业务表 |
| IoT/支付/推送资质与资料未到位（R-01/R-02/R-04） | R01/R02/R06/R27/R35/R41/R43 无法端到端验收 | 先接口抽象 + 模拟设备/沙箱；按附件二“暂缓/补验”留痕 |
| 电子签/团购接口未定（R-03/R-05） | R05/R14 无法真实验收 | 同上；先完成接口与留痕，真实渠道后补 |
