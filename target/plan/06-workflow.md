# 06 · 开发工作流与证据留痕

> 目标：小步提交、可追溯、可验收。适用于当前原型工程与后续 yudao 工程。

## 1. 分支模型

- `main`：随时可构建的稳定主线；规划文档与已验收增量在此。
- `feat/<模块>-<R编号>`：一个功能模块/需求；例 `feat/gym-store-R29`。
- `fix/<问题>`、`docs/<主题>`、`chore/<事项>`。
- 合并前：本地通过校验、`01-status.md` 已更新、无超范围改动；经评审（如有）再并入 `main`。

## 2. 提交规范

- 中文 conventional commits：`feat|fix|refactor|docs|chore|test(scope): 描述`。
- **一个可验证增量 = 一次提交**；提交信息带 R 编号，例：`feat(gym): 会员卡种 CRUD (R30)`。
- 不提交密钥/凭证/真实会员数据；大文件与构建产物不入仓。

## 3. 提交前自检（当前原型工程）

```bash
pnpm vsh lint --format
pnpm --filter @vben/web-antd typecheck
pnpm vitest run apps/web-antd --dom
```

> 后端工程落地后补充对应命令（Maven 构建、单测、接口冒烟），并在本文件与 `AGENTS.md` 同步。

## 4. 完成定义（DoD）

一个增量视为完成，需同时满足：

1. 功能按已确认需求可用（对应 R 编号）。
2. 权限与门店/数据范围校验通过（越权用例被拒绝）。
3. 有单元测试或可复现证据。
4. `target/plan/01-status.md` 更新。
5. 未接入的第三方能力明确标注“未接入”，**禁止假成功**。

## 5. 周报模板（合同第 3.5 条要求）

```text
第 N 周周报（YYYY-MM-DD ~ YYYY-MM-DD）
- 本周完成：<模块/增量>（R编号），证据/提交号
- 进行中：<模块>，预计完成日
- 阻塞/风险：<事项>，需甲方/第三方提供
- 下周计划：<模块/增量>
- 付款/变更记录：<如有>
```

## 6. 验收证据登记

- 每个 R 需求建立“R 编号 → 测试用例 → 证据（截图/日志/录屏/报告）”，对应附件二逐项结论（通过/整改/暂缓/不适用）。
- 第三方未就绪项按合同第 5.6 条记录：已完成软件工作、待提供条件、补验安排、款项处理；**“暂缓”不等于“通过”**。
- 里程碑 A/B/C 分别整理交付检查表，作为对应期次付款证据。

## 7. 文档维护

- 动态进度 → `01-status.md`；范围 → `02-scope.md`；架构 → `03-architecture.md`；排期 → `04-roadmap.md`；决策 → `05-decisions.md`。
- 合同范围变化必须同步 `02-scope.md` 并在 `05-decisions.md` 记录是否已签补充协议。
